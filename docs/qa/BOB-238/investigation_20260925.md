1. New executable guard `scripts/hooks/unattributed-commit-guard.sh` (237 lines, new file), which
   implements exactly the described check: closed bare/templated pattern set (`^Auto-commit$`,
   `^sync:[[:space:]]`), structure-not-substring matching (§11.4.201(7)(a)), a ticket/task-PR reference
   exemption, and a `--self-test` mode implementing §11.4.107(10) golden-good/golden-bad/false-positive

2. Companion doc `docs/scripts/unattributed-commit-guard.md` (new, 82 lines) and hermetic executing test
   `tests/hooks/test_unattributed_commit_guard.sh` (new, 140 lines) driving the REAL invocation path
   (not a `bash -n` parse check), with a documented paired §1.1 mutation.
3. Real-history proof: run against this repo's actual git log, the guard names the 14 unattributed
   commits since the last tag exactly as the commit message claims ("BOB-106/107: two guards built. The
   commit guard names 14 unattributed commits since the last tag").

> `# names as candidates) — both are outside this authoring pass's granted`

> `# item's closing step; see the BOB-106 tracker entry.`

Cross-checked mechanically: `scripts/pre_build_verification.sh` IS touched by this commit (164 lines

finds the string ONLY inside: the guard script itself, its `docs/scripts/*.md` companion doc,
`tests/hooks/test_unattributed_commit_guard.sh` (a test that invokes the guard directly, not a

**sibling item BOB-162** (filed in this same commit; see below), which independently states: "Neither is

## BOB-110 — "BOB-074 followup: UX-class test coverage (accessibility/usability) absent"

**Verdict: (a) — the commit already closes it.**

**Item's stated acceptance (from `docs/Issues.md`):** "`docs/testing/test_type_matrix.md`'s §11.4.27
test-type audit found UI functional coverage (Vitest + Playwright) but nothing framed around
usability/accessibility/UX outcomes specifically. Scope an axe-core or equivalent accessibility pass over
the Angular frontend, covering WCAG checks, keyboard-nav coverage, and screen-reader labeling."

**Citing evidence:**

1. `git show 7b45113 --stat` shows a brand-new `tests/ux/` suite: `conftest.py` (137 lines),
   `test_accessibility_axe.py` (141 lines), `test_keyboard_navigation.py` (111 lines),
   `test_live_dashboard_accessibility.py` (72 lines), 4 fixture HTML files (good/bad pairs for
   accessibility and keyboard-nav), plus `docs/testing/ux_accessibility.md` (187 lines, new
   documentation) and `frontend/package.json`/`package-lock.json` changes adding `axe-core` as a real
   npm devDependency (not vendored by hand).

2. `docs/testing/ux_accessibility.md` (new this commit) explicitly maps its coverage table against the
   3 named acceptance criteria:
   - **WCAG checks** — real `axe-core` scan of a real Playwright-rendered, JS-hydrated DOM: image
     alt-text (`image-alt`), form-control labels (`label`), colour contrast (`color-contrast`), single
     `<h1>`/heading order (`heading-order`), `<html lang>` (`html-has-lang`).
   - **Keyboard-nav coverage** — real `page.keyboard.press("Tab")` traversal asserting on
     `document.activeElement.id`, plus real computed `:focus-visible` style checks
     (`outlineStyle`/`outlineWidth`/`boxShadow`) read after a real Tab press.
   - **Screen-reader labeling** — covered via axe's accessible-name/ARIA-resolution rule set (the doc's
     own oracle-selection table states the chosen oracle "Implements the actual WCAG 2.x success
     criteria (real computed contrast, real ARIA resolution, real accessible-name computation)"), plus
     the `label` and `image-alt` rules directly assert screen-reader-relevant labeling.

3. Anti-bluff RED→GREEN evidence pasted in the doc: `a11y_good.html`'s alt attribute was removed, the
   golden-good suite observed to FAIL on `image-alt`, the file restored with a verified byte-identical
   `sha256sum` match, then re-observed to PASS.

4. Golden-FALSE (negative control) cases are documented and asserted: a decorative `alt=""` image and an
   `aria-hidden="true"` icon inside an `aria-label`-carrying button are both proven NOT flagged, proving
   the oracle discriminates rather than blanket-failing the fixture.

5. The suite found a REAL defect on the first live run (21 WCAG AA colour-contrast violations on the
   dashboard) and, per §11.4.238 (automated QA must be the discoverer), left the assertion honestly
   FAILING rather than silencing it — this is the correct, constitution-mandated behaviour for newly
   discovered coverage, not a sign BOB-110 itself is incomplete: the item's acceptance text only asks to
   *scope* the accessibility pass, not to guarantee the underlying app has zero accessibility defects.

6. Confirming that the discovered defect was NOT lost and was NOT conflated with BOB-110's own scope: a
   separate tracked item, `BOB-164` ("Live dashboard fails WCAG AA colour contrast on 21 nodes — brand
   heading measures 1.43:1 against a 3:1 floor"), exists in `docs/Fixed.md` with
   `**Created-By:** BOB-110 UX-class coverage, discovered by the new axe-core suite on its first live run`
   — and BOB-164 has since been independently CLOSED (it lives in `Fixed.md`, not `Issues.md`). This
   confirms the discovery→tracked-item→fix pipeline worked exactly as the constitution mandates, and that
   the found defect is fully accounted for outside BOB-110's own scope.

**Assumption:** BOB-110's acceptance text does not explicitly require covering every route/dialog in the
Angular app; the doc itself lists honest gaps (only the dashboard landing view scanned live; the
`ng serve`-hosted route set not scanned directly — a documented, reasoned scope narrowing, not a silent
omission). I read BOB-110's acceptance as "scope [build] an accessibility pass covering these three
classes of check" (which was done, comprehensively, with real oracle proof), not as "achieve zero
accessibility violations across the whole app" (which is explicitly BOB-164's separate, already-closed
scope). Under that reading the verdict is (a).
