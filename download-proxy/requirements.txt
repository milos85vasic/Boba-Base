# Runtime dependencies for the download-proxy / merge-search service
# (download-proxy/src), installed INTO the stock `python:3.12-alpine` image at
# CONTAINER START by start-proxy.sh:
#
#     pip install --quiet --no-cache-dir -r /config/download-proxy/requirements.txt
#
# `./download-proxy` is bind-mounted at `/config/download-proxy`
# (docker-compose.yml), so THIS file is the one the container reads. There is
# no image build and no baked dependency layer: whatever this file resolves to
# at restart time IS production.
#
# ---------------------------------------------------------------------------
# WHY EVERY VERSION IS PINNED (BOB-154) — this file used to carry `>=` floors
# with no ceiling and no lock, which made the resolved set a function of the
# INSTALL DATE rather than of this file. Measured 2026-08-21:
#
#     host .venv installed 2026-08-07 23:12  ->  starlette 1.4.1, uvicorn 0.52.1,
#                                                idna 3.18,  filelock 3.32.2, ...
#     container  installed 2026-08-21 15:20  ->  starlette 1.6.0, uvicorn 0.52.4,
#                                                idna 3.19,  filelock 3.32.3, ...
#
# Eight packages diverged — exactly the ones that shipped a release in the
# 14 days between the two installs. Every test run on the host was therefore
# evidence about a dependency set production does not run. Worse, because the
# install happens at every container start, an unpinned file re-rolled the dice
# on EVERY restart: the divergence regenerated itself, differently each time,
# and nothing anywhere reported it.
#
# Pinning is the correct shape here because this is an APPLICATION, not a
# library: applications pin so that the artifact is reproducible, libraries
# float so that consumers can resolve. A `>=`-floored application requirements
# file is the defect, not a stylistic preference.
#
# HOW THESE VALUES WERE CHOSEN (§11.4.6 — measured, never guessed): they are
# the set the production container was ALREADY running on 2026-08-21, read out
# of the live container with `pip list --format=freeze`. That matters for
# safety: every one of these versions is proven installable on this exact
# `python:3.12-alpine` image, because it was installed there. Re-resolving to
# the same versions on the next restart cannot fail to build.
#
# HOW A ROTTED PIN GETS NOTICED (a pin nothing maintains is its own defect):
# `scripts/scan.sh` already runs `pip-audit -r download-proxy/requirements.txt`
# and writes JSON + SARIF to the artifact dir. Against the old `>=` floors
# pip-audit had to resolve to "latest" — a moving target that was not what
# production ran, so its verdict described a set nobody was running. Against
# these pins it audits EXACTLY the production set and names the exact version
# to raise. Pinning strictly improves the signal that already existed; it does
# not create a new promise nobody keeps.
#
# HOW TO RAISE A PIN: change the version here, restart the container, then
# reconcile the host venv with the SAME file so the two stay in step:
#     ./start.sh --recreate                       # container re-resolves
#     .venv/bin/python -m pip install -r download-proxy/requirements.txt
#     bash scripts/pre_build/check_cm_runtime_deps_parity.sh   # must PASS
#
# The parity gate (CM-RUNTIME-DEPS-PARITY) compares the two REAL resolved sets
# and fails loudly when they drift apart again, so this pin is not the only
# thing standing between the project and a repeat of BOB-154.
# ---------------------------------------------------------------------------
